## 🔳 Codex - gpt-5.5
**Bottom line:** the sequence is directionally right, but the plan is too optimistic where hand-authored content, the shared challenge renderer, deploy friction, and QA/video all collide. The biggest adversarial correction: move a minimal deploy smoke test earlier, make Phase 2 less ambitious or longer, and treat “hour 8 spine not navigable” as a command to abandon styled flow-order work immediately.

**Findings**

**Critical: Phase 6 leaves deployment risk too late.**  
[PROJECT_PLAN.md](/Users/rajatarora/Projects/FinePrint/factory/artifacts/PROJECT_PLAN.md:233) puts Vercel, the serverless function, env vars, clean-browser testing, and phone testing in a 1.5h final phase. That is not credible. Even if the code is fine, the failure modes are external: Vercel project config, static routing, serverless path shape, env var visibility, CORS-ish mistakes, production/dev flag mismatch, phone viewport surprises.

Recommendation: add an early “deploy empty shell” checkpoint after Phase 1 or Phase 2:

```txt
After Phase 1:
- Deploy static shell to Vercel.
- Confirm hash routing works on production URL.
- Confirm Start Over/localStorage works on production.
- Add stub /api/coach returning { source: "fallback-deterministic", message }.
```

Then Phase 6 becomes “turn on live Gemini and verify,” not “discover whether deployment works.”

**Critical: Phase 2 is under-budgeted and gates everything.**  
Phase 2 asks for the validator, the full lesson JSON, ten exact excerpts, vocabulary, three challenge types per excerpt, decoys, reconstruct clues, closing statement slots, whose-words metadata, negative tests, and source-file scanning in 3 hours ([PROJECT_PLAN.md](/Users/rajatarora/Projects/FinePrint/factory/artifacts/PROJECT_PLAN.md:79)). For one person, this is the most likely phase to blow up because it combines programming, close reading, puzzle design, and QA.

The validator itself may be manageable. The authored lesson is the danger. Bad content is not a “fix later” issue because later screens depend on its shape.

Recommendation: split Phase 2 internally:

```txt
2A. Schema + validator + 1 complete excerpt fixture.
2B. Full lesson authoring.
2C. Negative validator tests.
```

Do not let 2C block visual wiring if 2A/2B are basically sound, but do not ship without it.

**Major: The tripwire says “cut re-read,” but re-read is already not in the build.**  
The plan repeats the locked cut order at [PROJECT_PLAN.md](/Users/rajatarora/Projects/FinePrint/factory/artifacts/PROJECT_PLAN.md:31), but P1 re-read, voice, and moving lamp are already out or after submission. If hour 8 arrives and the spine is not navigable, cutting them buys almost nothing.

The real hour-8 action should be operational:

1. Stop styled flow-order work.
2. Force all nine routes to exist with placeholder UI.
3. Make one generic challenge component handle all challenge types, even if visually plain.
4. Use deterministic coach only.
5. Ship static lamp, no parallax, no animation except book-open/book-close.
6. Defer all decorative shelf/spine polish.
7. Deploy immediately after the mechanical flow works.

That is the actual save.

**Major: Phase 4 is the second likely blow-up.**  
The shared renderer has to support word lock, object search, cite-the-line, wrong-answer rewind, revealed evidence, nudge limits, first-attempt scoring, retries, and a ten-excerpt loop ([PROJECT_PLAN.md](/Users/rajatarora/Projects/FinePrint/factory/artifacts/PROJECT_PLAN.md:156)). Four hours is possible only if the renderer is extremely plain and the lesson schema is stable.

Trade-off: one beautiful custom word lock plus bespoke cite UI is fatal. A plain but consistent “choose object / choose dial / choose line” renderer is shippable.

A safer implementation shape:

```js
const challengeHandlers = {
  wordLock: renderSingleChoiceChallenge,
  searchRoom: renderMultiChoiceChallenge,
  citeLine: renderLineChoiceChallenge,
  reconstruct: renderMultiChoiceChallenge,
};

dispatch({
  type: "SUBMIT_ATTEMPT",
  challengeId,
  selectedIds,
  evidenceLineId,
  at: Date.now()
});
```

Screens should never know whether the attempt is scoring-valid; they only dispatch. The reducer decides.

**Major: Some acceptance criteria are too subjective to be testable.**  
Examples:

- “No outside instruction” ([PROJECT_PLAN.md](/Users/rajatarora/Projects/FinePrint/factory/artifacts/PROJECT_PLAN.md:63)) needs a test method: one cold click-through by the developer, or one observer.
- “Deterministic coach good enough to be the normal experience” ([PROJECT_PLAN.md](/Users/rajatarora/Projects/FinePrint/factory/artifacts/PROJECT_PLAN.md:211)) needs concrete checks: under 90 words, names one weak skill cluster, gives one next action, contains no story text.
- “Wrong word making the sentence untrue” ([PROJECT_PLAN.md](/Users/rajatarora/Projects/FinePrint/factory/artifacts/PROJECT_PLAN.md:206)) is content-reviewable, not mechanically testable unless the lesson has authored truth labels.

Turn these into checklists, not vibes.

**Major: P0-3 rereading is underspecified.**  
The PRD requires “Rereading is always permitted; revealed text stays on screen” ([PRD.md](/Users/rajatarora/Projects/FinePrint/factory/artifacts/PRD.md:114)). The plan covers wrong-answer rewind and revealed text ([PROJECT_PLAN.md](/Users/rajatarora/Projects/FinePrint/factory/artifacts/PROJECT_PLAN.md:172)), but it does not explicitly require an always-available reread affordance during challenges.

Add acceptance:

```txt
Every challenge has a visible reread/review action.
Using it does not affect score, timer, or firstAttempts.
Previously revealed evidence remains visible after returning.
```

**Major: PRD P0-4 “identifiable in isolation” is missing from plan acceptance.**  
The PRD says every target object must be identifiable after one read ([PRD.md](/Users/rajatarora/Projects/FinePrint/factory/artifacts/PRD.md:123)). The plan says decoys are real story elements, but does not test whether targets are visually/textually distinguishable.

Add human-readthrough criterion: for every object/person choice, the label or image must distinguish it without relying on hidden title text or author memory.

**Minor: “Not one word of story text exists in HTML or JS” is over-literal.**  
[PROJECT_PLAN.md](/Users/rajatarora/Projects/FinePrint/factory/artifacts/PROJECT_PLAN.md:148) says “not one word,” but common words are unavoidable. The locked rule is really no story phrases, quotes, citation text, or evidence text in source files; scan phrases over about 12 characters. Use the locked wording so the test is implementable.

**Most Credible Reorder**

I would adjust the order like this:

```txt
1. Spine + reducer + localStorage + all routes.
1.5. Minimal Vercel deploy with stub /api/coach.
2. Validator + lesson schema + one complete excerpt.
3. Full lesson JSON.
4. Shared challenge renderer, plain.
5. Read/vocabulary styling.
6. Finale/report deterministic.
7. Live coach.

```

This violates the emotional preference to style in flow order, but only after the spine exists. It protects the submission.

**If Hour 8 Arrives And The Spine Is Not Navigable**

Do this, in order:

1. Stop all visual polish.
2. Remove parallax, room depth, decorative shelf polish, custom lock animation.
3. Build all nine routes as plain panels with Next buttons.
4. Make the shared renderer support only essential choice modes: single choice, multi choice, line choice.
5. Keep all P0 mechanics: read, challenges, finale solve, Case Report, content validation.
6. Deploy deterministic-only; live coach can be added after a full production playthrough.
7. Keep the demo path narrow: one wrong answer rewind, one cite-line, finale, report.

Do not cut the challenge types, validator, finale, or Case Report. Cut presentation ambition first, integration novelty second, AI live polish third. The project wins by proving the reading loop, not by matching every comp.
